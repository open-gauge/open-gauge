Un **procedimiento** es una plantilla reutilizable de procedimiento de calibración, delimitada a una magnitud física
(p. ej. un proceso documentado para calibrar RTDs de temperatura contra una referencia de bloque seco).
Gestiónalos desde la página **Procedimientos** en la barra lateral.

## Por qué existen los procedimientos

ISO/IEC 17025 exige que un laboratorio documente y siga procedimientos definidos para su trabajo de
calibración. Las plantillas de procedimiento de Open Gauge capturan esa documentación una sola vez y te permiten
referenciarla desde cada calibración realizada de la misma manera, en lugar de volver a escribir las notas de
metodología cada vez.

## Campos

| Campo | Propósito |
|---|---|
| Nombre y magnitud física | Qué calibra este procedimiento, y para qué magnitud. |
| Versión | Cadena de texto libre de versión (p. ej. `"1.0"`) — increméntala cuando cambie la metodología. |
| Dificultad | Guía informativa de nivel de habilidad para quien lo realice. |
| Referencia de norma | Referencia de texto libre a una norma externa (un número ISO/ASTM, etc.). |
| Autor, duración | Quién lo escribió, y aproximadamente cuánto tiempo toma realizarlo. |
| Etiquetas | Etiquetas de formato libre para búsqueda/filtrado. |
| Equipo | Lista estructurada del equipo requerido. |
| Materiales | Lista estructurada de materiales/consumibles requeridos. |
| Entorno | Condiciones ambientales requeridas (temperatura, humedad, etc.) bajo las cuales realizar el procedimiento. |
| Notas de seguridad | Lista de texto libre de consideraciones de seguridad. |
| Pasos | Los pasos ordenados del procedimiento en sí. |
| Criterios de aceptación | Qué cuenta como aprobado para este procedimiento, documentado junto a él. |

## Descargar un procedimiento como PDF

Cada procedimiento tiene un botón **Descargar PDF** junto a **Editar** en su página de detalle:
genera al momento un PDF con los datos actuales del procedimiento (metadatos, equipo requerido,
materiales, condiciones ambientales, instrucciones de seguridad, pasos y criterios de aceptación),
listo para imprimir y llevar al campo.

El PDF proviene de una plantilla de documento de tipo **Procedimiento de Calibración** publicada y
activa (ver [Plantillas de documento](../templates/index.mdx)) — el mismo editor WYSIWYG usado
para las plantillas de certificados, con un conjunto de variables propio del procedimiento
(equipo, metadatos del procedimiento, entorno, pasos, criterios de aceptación, instrucciones de
seguridad, fechas). Por defecto se genera con la plantilla marcada como **Predeterminada** en
**Admin → Plantillas → Procedimientos**; el menú desplegable del botón de descarga te permite
elegir otra solo para esa descarga, una elección puntual que no cambia la predeterminada guardada.
Cada instalación comienza con una **plantilla base** permanente e incorporada (ver
[Gestionar plantillas](../templates/index.mdx#gestionar-plantillas-base-predeterminada-y-activa))
que cubre todos los campos del modelo de Procedimiento y es la predeterminada hasta que un
administrador marque otra — de modo que la descarga funciona desde el primer procedimiento, antes
de que nadie haya diseñado una plantilla propia.

A diferencia de un certificado de calibración, un PDF de procedimiento documenta el *método*, no un
evento de calibración concreto: no lleva firma digital ni bloque de firma del técnico/verificador.

## Vincular un procedimiento a un canal

En un canal de sensor, establece **método de calibración** a un procedimiento guardado — esto se convierte en el
procedimiento *por defecto* del canal, preseleccionado cada vez que inicias una nueva calibración interna para
ese canal. Es solo un valor por defecto: cualquier calibración puede referenciar un procedimiento diferente (o
ninguno) si la situación lo requiere.

## Dónde aparecen los procedimientos en una calibración

Una calibración **interna** (consulta
[Resumen de calibración](../calibration/overview.mdx)) puede referenciar el procedimiento que se
siguió (`internal_procedure_id`), y esa referencia se imprime en el certificado resultante junto al
patrón de referencia utilizado y las condiciones ambientales registradas — la cadena de trazabilidad
completa que necesita un certificado de calibración.

## Importar y exportar

Disponible solo para usuarios **admin** y **superadmin**. Cualquier procedimiento se puede exportar
como un paquete ZIP — desde el botón **Exportar** junto a **+ Nuevo procedimiento** en la página de
Procedimientos para exportar en bloque una selección (un modal de casillas te permite elegir
procedimientos individuales o seleccionarlos todos a la vez), o desde **+ Nuevo procedimiento →
Importar desde archivo** para un solo procedimiento a la vez. Una exportación en bloque es
simplemente varios paquetes de un solo procedimiento dentro de un ZIP exterior, así que se puede
volver a importar de la misma manera en que se exportó.

Cada procedimiento obtiene su propia carpeta con el nombre de su `proc_id` (p. ej.
`PROC-TEMP-001/`), que contiene:

- **`procedure.yaml`** — todos los campos del procedimiento (nombre, versión, dificultad,
  referencia de norma, etiquetas, equipo, materiales, entorno, notas de seguridad, pasos y
  criterios de aceptación), en un formato legible por humanos.
- **`media/steps/{n}/`** — los bytes reales de cualquier archivo adjunto al paso `n` (imágenes,
  PDFs, etc.), una subcarpeta por índice de paso.

**Lo que se omite deliberadamente de `procedure.yaml`**: los UUID internos de la base de datos —
el id propio del procedimiento, `created_by` y el id de cada archivo. Estos solo tienen sentido
dentro de la base de datos de la que provienen.

### Importar

Importa un ZIP desde **Procedimientos → + Nuevo procedimiento → Importar desde archivo** (espera
exactamente un procedimiento en el archivo) o desde el botón **Importar** de la página (acepta uno
o más ZIPs a la vez, cada uno de los cuales puede contener a su vez una o más carpetas de
procedimiento — útil para volver a importar una exportación en bloque anterior). Ambos flujos
llaman al mismo endpoint del backend y reportan un resultado por carpeta de procedimiento, de modo
que un problema con un procedimiento nunca bloquea a los demás del mismo archivo.

Al importar, se crea un procedimiento completamente nuevo con un id interno nuevo. Si el `proc_id`
exportado ya existe en el sistema destino, la importación de ese procedimiento falla con un error
claro — renómbralo en el YAML y vuelve a intentarlo.
